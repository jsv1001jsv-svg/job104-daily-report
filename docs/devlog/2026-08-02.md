反過來說，若今天先攻 Cloudflare 而失敗，等於一天下來既沒抓到資料，
其他模組也依然沒有安全網。

### 測到的關鍵規則

補測試的過程中，把幾條「錯了會造成資料遺失」的規則明確釘住：

1. **推播成功才標記已看過**（`test_推播失敗不標記已看過以便明天重試`）
   順序反過來的話，LINE 額度用完那天的職缺會永遠不再出現。
2. **單一使用者失敗不影響其他人**（`test_一位使用者抓取失敗不影響其他人`）
   一個人的搜尋條件打不到 104，不該讓其他人收不到日報。
3. **webhook 處理失敗仍回 200**（`test_單一事件失敗仍回_200`）
   回 500 會讓 LINE 不斷重送整批事件，造成重複處理。
4. **各使用者的已看清單互不影響**（`test_各使用者的已看清單互不影響`）
   多使用者版的核心前提。
5. **摘要失敗降級而非拋例外**
   使用者收到品質稍差的日報，好過收不到日報。

## 踩到的坑

### 1. `slots=True` 的 dataclass 沒有 `__dict__`

想用 `Job(**{**job.__dict__, "description": ...})` 快速造變體，直接 `AttributeError`。

**原因**：`@dataclass(slots=True)` 用 `__slots__` 取代實例字典，省記憶體也擋住動態加屬性。
**解法**：改用 `dataclasses.replace(job, description=...)`，本來就是 frozen dataclass 的正規做法。

### 2. host 上沒有專案依賴

Docker Desktop 沒開，`python -m pytest` 直接 `ModuleNotFoundError: pydantic_settings`。

**解法**：建 `.venv`（已在 `.gitignore`）跑單元測試。
單元測試不碰容器內的服務，host 上跑結果一致，回饋快很多。
整合測試（Firestore 模擬器）仍需走 Compose。

### 3. 測試讀到本機 `.env` 導致結果不穩

`Settings` 預設 `env_file=".env"`，測「缺少金鑰時應拋錯」時，
本機 `.env` 有值就不會拋，測試在別人機器上會壞。

**解法**：測試一律用 `Settings(_env_file=None, ...)` 明確給值，不依賴環境。

# 下午：Cloudflare 解決了

## 結論先講

**Cloudflare 擋的是 TLS handshake 指紋，不是 header。**
改用 `curl_cffi`（模仿 Chrome 的 handshake）純 HTTP 直接通過，
不需要瀏覽器。Playwright 整層已移除。

---

## 怎麼找到的

### 1. 先試便宜的：其他子網域

昨天已知 `static.104.com.tw` 沒有防護，代表防護是**逐子網域**設定的。
所以先花十分鐘掃一輪候選子網域，看有沒有沒設防的 API host：

| 子網域 | 結果 |
| :--- | :--- |
| `www.104.com.tw` | 🔴 Cloudflare 挑戰 |
| `static.104.com.tw` | 🟢 無防護（已知） |
| `mobile.104.com.tw` | 🟢 無防護，直接回 JSON |
| `pda.104.com.tw` | 🟡 200 但不是 JSON |
| `m` / `api` / `mapi` / `app` / `open` / `data` / `jobs` | DNS 不存在 |

`mobile.104.com.tw` 看起來很有希望——不在 Cloudflare 後面（IP 是 AWS 而非
Cloudflare 的 104.18.x 段），根路徑直接回 JSON。但深入探測後是死路：
**不論什麼路徑都回同一份「版本不存在」的公告 JSON**，它是 App 的版本檢查
端點，不是職缺 API。已排除並記入 CLAUDE.md 5.1 的「被否決的方案」。

### 2. 查「被擋的原因」而不是找「更強的工具」

順手查了一下 Cloudflare 的判別機制，關鍵字是 **JA3/JA4 TLS 指紋**。

這一下就對上了昨天最令人困惑的那個現象：**用真的 Chromium，頁面自己發出的
API 請求照樣 403**。如果連真瀏覽器都被擋，那被檢查的東西就不在「請求長什麼樣」。

TLS 指紋的意思是：每個 HTTP 客戶端建立加密連線時，會送出一組自己特有的參數
組合（支援哪些加密套件、什麼順序、帶哪些擴充欄位）。Python 的 TLS 函式庫和
Chrome 差很多，比對一下就知道對面不是瀏覽器。**這發生在任何 header 被送出
之前**，所以 header 補得再滿都沒用。

### 3. 驗證假說

`curl_cffi` 是 curl-impersonate 的 Python 綁定，會照 Chrome 的方式做 handshake。
寫了個對照實驗，同一支 API、同一組 header，只差在客戶端：

```
對照組 httpx（Python 原生指紋）      → 🔴 Cloudflare 挑戰頁
實驗組 curl_cffi(impersonate=chrome) → 🟢 拿到 JSON，31 筆職缺
```

**第一發就中。**

## 踩到的坑

### Windows 終端機印不出 ✓ 與 emoji

探測腳本一跑就 `UnicodeEncodeError: 'cp950' codec can't encode character '✓'`。

**原因**：Windows 主控台預設 cp950（Big5），非 Big5 字元直接炸。
**解法**：執行時加 `PYTHONIOENCODING=utf-8`。

---

## 這件事的教訓（值得記下來）

昨天花一整天在 Playwright 上，方向是錯的。錯在**沒有先問「被擋的原因是什麼」
就開始找「更強的工具」**——從 httpx 換到真瀏覽器，是把賭注加大，不是把問題查清楚。

而真正有用的那條線索（**真瀏覽器發的請求也被擋**）昨天就已經觀察到了，
還寫進了 CLAUDE.md。但當時把它解讀成「瀏覽器還不夠像真人」，
於是繼續往反偵測方向加碼（xvfb、UA 對齊、persistent profile⋯⋯）。

如果當時停下來問一句「連真瀏覽器都被擋，那被檢查的到底是什麼？」，
答案會來得快很多。**異常現象是線索，不是待克服的障礙。**
